    OPQ-128 — No key-domain separation between the auditing RNG namespace and the mechanism RNG namespace. _coin_flip.py:143-146 · privacy-correctness · ε:no (today) · PLAUSIBLE. coin_flip derives canary selection from np.random.default_rng(key.seed) and the coin flips from np.random.default_rng(fold_in(key, 1).seed) — neither carrying a domain-separation tag. The DP-SGD noise stream uses rng_fold_in(st._rng_key, st._step_counter) with the counter starting at 0, so step 1 uses fold_in(key, 1) — byte-identical key material to the coin flips, and examples/train_dpsgd.py:1191 passes key(args.seed) to coin_flip while :1689/:1694 pass key(args.seed) to gaussian_noise. The one-run theorem requires the coin vector S to be independent of the mechanism's internal randomness. Fix: derive both auditing streams through a string tag — fold_in(key, 'opaque.auditing.canary_select') and fold_in(key, 'opaque.auditing.coin_flip') — and document in the user guide that the audit key must be independent of the training key (fold_in already accepts str tags, so the mechanism exists and is simply unused). Notes: measured no exploitable dependence today (P(canary in batch 1) = 0.04988 under a shared seed vs 0.04999 under independent seeds over 400 trials), because the two consumers draw from different generator families (numpy PCG64 vs a torch Generator seeded seed % (2**63-1)). affects_epsilon should be false — no current estimate is biased. The exposure is forward-looking: any future change moving the coin flips onto a torch generator would silently make S a low-entropy image of the value driving the noise, with no test able to catch it. One evidence item is wrong: the shipped example seeds PoissonSampler with fold_in(key(args.seed), rank, epoch) (train_dpsgd.py:1739), not key(args.seed) — that collision exists only across two docstrings, and it affects which rows are canaries, not the coin vector, so it is not an independence violation.

    Auditing¶

    • _gdp._compute_v_k numerical integration is correct. Validated against the exact identity Σ_k E[g(Y_(k))] = n·E[g(Y)] (which holds for any g and n) at the default grid_size=10000 across μ ∈ {0.01, 0.5, 2.0, 5.0} and n ∈ {10, 100, 500, 1500, 10000}: relative error never exceeded 3e-4, and its sign is negative (v_k slightly under-estimated) — the conservative direction.

    4. Refuted candidates¶

    Sixteen findings were investigated and dismissed. Recorded so they are not re-raised.

    1. "Bounded Gaussian is a data-dependent renormalized truncation → ε understated" (three separate submissions, _gaussian.py). Refuted by direct computation. The log(Z(μ)/Z(μ')) term is real, but it is more than offset by the tail removal that produces it — which none of the three submissions computed. Because the output is confined to [low, high], the privacy loss is a bounded linear function of the output rather than the Gaussian's unbounded quadratic, so the bounded mechanism satisfies pure ε-DP and its δ hits exactly 0 at moderate ε. Worked examples: σ=1, bound=(0,10), μ=0 vs μ'=1 → δ at ε=0.5 is 0.0894/0.1465 vs the Gaussian's 0.2384; at ε=1.0, 0.00016/0.0650 vs 0.1269; total variation 0.2771 vs 0.3829. σ=1.1, bound=(−3,3), sensitivity 1 → at ε=3.0 the Gaussian has δ=4.73e-4 and the bounded mechanism has exactly 0. Over a 2620-point random sweep of σ, asymmetric bounds, ε and centre pairs within the clip ball, max δ_bounded/δ_gaussian = 1.0000009 (quadrature noise). By monotonicity of f-DP composition this domination carries through the per-coordinate product and the T-step composition, so dpsgd_acc.gaussian() is a valid upper bound and the shipped examples are not publishing an invalid guarantee. One submission also used an unreachable centre pair (x=1 → x'=2 with bound=(−2,2)), since the per-coordinate centre is bounded by clipped.max_norm = 1.0 there. (The genuinely confirmed bounded-Gaussian issues are OPQ-011, float32 saturation, and OPQ-012, the missing derivation — see the honesty note there.)
    2. "likelihood_ratio_warm indexes past its DP array and panics whenever n_steps <= bands − 2." _band_mf.py:84-86 rejects bands > n_steps when the strategy coefficients are materialised, and that happens inside _pld_at_horizon before the native call; combined with rounded = min(ceil(n_steps/bands)*bands, self.n_steps) >= bands, the argument passed to Rust always satisfies n >= bands.
