# Issue 377: explicit canary selection for coin-flip audits

Research snapshot: 2026-08-25. The target is
[issue #377](https://github.com/JetBrains-Research/opaque/issues/377),
“Provide explicit canary construction for coin-flip audits,” under the broader
[auditing rebuild tracker #327](https://github.com/JetBrains-Research/opaque/issues/327).
It is open, unassigned, and labelled as a low-severity auditing enhancement and
test gap; the milestone is Slate.

## Conclusion

Opaque should keep `coin_flip` responsible for statistical partitioning and let
the caller remain responsible for constructing or selecting examples. The
smallest useful public extension is an optional `candidate_indices` pool:

```python
cf = auditing.coin_flip(
    audited_dataset,
    num_canaries=len(crafted_canaries),
    key=key(42),
    candidate_indices=range(len(dataset), len(audited_dataset)),
)
```

This supplies the missing composition point without pretending a generic
auditing package knows how to build a difficult image, text record, preference
pair, or gradient for a particular model. The membership labels must still be
independent fair coin flips generated by Opaque. An API for caller-chosen
membership masks would change the statistical experiment and is not part of
this fix.

The implementation should also replace the package README's two “canary
injection” claims with “canary partitioning,” document the default natural-row
audit as a valid but potentially low-power lower bound, and make all four
training examples state that a low result from their natural canaries is not a
privacy certificate.

## What the issue actually establishes

At the issue baseline, `coin_flip(dataset, num_canaries, key)` uniformly
selects existing dataset rows, assigns each an independent Bernoulli(1/2)
membership bit, and removes the tails from training. It neither creates records
nor appends anything to the dataset. Nevertheless,
`packages/opaque-auditing/README.md` advertised “coin-flip canary injection.”
There was no supported way to restrict selection to records a caller had
constructed:

- `CoinFlip` is exported as a state carrier, but constructing it directly
  requires the private `_in_mask` field and correctly synchronized derived
  arrays.
- The reference guide documents a `CoinFlip(canary_indices, *, key)`
  constructor that does not exist.
- `train_dpsgd.py`, `train_dpftrl.py`, `train_sft.py`, and `train_dpo.py` all
  use uniformly selected natural training rows without explaining what a low
  result can mean.

Issue #377 therefore combines a terminology defect, a missing public selection
seam, and an interpretation gap. Its stated acceptance criteria allow a
documentation-only resolution if Opaque stops claiming injection, but retaining
a documented path for stronger caller-supplied canaries is more useful and
requires very little new surface.

The issue has no discussion or linked pull request at this snapshot. Its source
identifiers, AUD-168 and OPQ-127, can be traced through the audit material
removed in [commit f398839](https://github.com/JetBrains-Research/opaque/commit/f398839).
That audit originally described the absence of construction as wholly negative,
but its verification recorded two corrections that materially reframe the fix:

1. the implemented reference-loss score is the loss-difference attack from the
   original paper; and
2. natural in-distribution canaries are a legitimate experimental variant, not
   a broken implementation.

The default should consequently remain backward compatible rather than being
replaced with a guessed synthetic-canary recipe.

## Statistical contract

The one-run experiment in
[Steinke, Nasr, and Jagielski (2023)](https://arxiv.org/html/2305.08846)
starts with a fixed base dataset and fixed canary set, independently samples one
fair membership bit per canary, trains once, and tests guesses of those bits.
Opaque's natural-row partition is equivalent: after canary selection, the
unselected rows form the base dataset and the selected rows form the canary
set.

The paper evaluates several very different canary designs:

- sparse, arbitrary gradient-space canaries for white-box audits;
- randomly relabelled input examples; and
- natural in-distribution examples.

It also reports that black-box input-space audits are weaker and that power can
fall both when there are too few canaries for statistical resolution and when
there are too many for the model to memorize. This rules out two tempting but
incorrect simplifications: natural rows are not invalid, and appending more
crafted rows does not monotonically improve the audit.

More recent work sharpens that point. Dagréou and Bellet's
[Detectability in Diversity (2026)](https://arxiv.org/html/2605.27292)
finds that effective one-run canaries need both high individual detectability
and low mutual interference. Influence-selected in-distribution records can be
substantially stronger than random natural records, while worst-case auditing
can benefit from optimized out-of-distribution canaries. The required
construction depends on the model, task, representation, and attack. Earlier
[tight-auditing work](https://arxiv.org/abs/2302.07956) likewise shows that
natural examples can support strong audits under suitable access and scoring.

These results support a selection API, not a universal constructor. A caller
may use a public proxy model, influence approximation, label perturbation, or a
domain-specific generator to build a candidate set. Opaque only needs to bind
that fixed set to the partition and its stable dataset indices.

### Conditions the public guide must preserve

1. **Precommit the pool.** Choose `candidate_indices` before target training and
   independently of the target run's membership coins and outputs. Selecting
   records after observing the trained target can leak the hidden labels into
   the experiment.
2. **Keep fair membership coins.** A reproducible RNG key is supported; an
   arbitrary caller-controlled in/out mask is not. The paper's fixed-size,
   paired alternative is a different experiment and would need its own
   estimator.
3. **Use one indexed dataset.** Partition, training-subset construction, and
   scoring must all refer to the same augmented dataset. The stable-ID work in
   [PR #543](https://github.com/JetBrains-Research/opaque/pull/543) prevents
   ordering mistakes but cannot repair indices from a different dataset.
4. **Account for the audited workload.** Adding or withholding canaries changes
   the data seen by the sampler. If sample probability, number of steps,
   minimum separation, number of bins, or another privacy-relevant setting is
   derived from the realized dataset size, accounting for one fixed
   configuration may not cover all neighbouring runs. The theoretical bound
   used for comparison must describe the actual audit mechanism, not the
   unaugmented training job.
5. **Treat the result as a lower bound.** A small audited epsilon can mean low
   leakage, weak scores, poorly chosen or interfering canaries, or insufficient
   statistical power. It is not evidence that the implementation satisfies a
   small epsilon.

The fourth condition is broader than “recompute the sample rate after
appending rows.” The repository audit groups this with the still-missing binding
between runtime samplers and their accounting contracts. This issue should warn
about the boundary, not claim to solve it.

## Options considered

| Option | Benefit | Adversarial finding |
|---|---|---|
| Rename “injection” and make no API change | Smallest possible resolution under the issue text | Leaves callers without a supported way to audit a preselected or constructed cohort |
| Add modality-specific canary constructors | Could offer convenient recipes | No recipe is meaningful across images, text, preferences, and gradient-space audits; it would add model/data dependencies to a generic package and could create a false sense of strength |
| Accept a caller-supplied membership mask | Gives exact in/out control | Violates the independent fair-coin experiment used by the current estimator |
| Add a second factory for exact canary indices | Statistically sound if it still flips fair coins | Duplicates partition logic and creates two public construction paths; mutual-exclusion rules with `num_canaries` add avoidable surface |
| Add `candidate_indices` to `coin_flip` | Handles constructed rows and selected natural cohorts while preserving one factory | Requires clear precommit, indexing, interference, and workload caveats |

The pool form also subsumes exact designation: when the pool length equals
`num_canaries`, every supplied index is a canary. When the pool is larger,
unselected pool records remain ordinary always-in data; this is valid, but it
can matter for canary interference and must be understood by callers.

## Chosen architecture

`coin_flip` gains one keyword-only argument:

```python
candidate_indices: Any | None = None
```

- `None` retains the historical `Generator.choice(dataset_size, ...)` call so
  existing keys reproduce the same canary indices and membership bits.
- A supplied pool must be one-dimensional, integer-valued, unique, and within
  `range(len(dataset))`.
- The pool is sorted before sampling, making it a set-like input whose order
  does not alter a seeded audit.
- `num_canaries` is sampled without replacement from the pool. It may equal the
  pool size, but not exceed it.
- Canary selection and membership continue to use their existing named RNG
  domains.
- `CoinFlip` remains a returned state object; the factory remains the supported
  constructor.

No dataset mutation helper is added. Appending or otherwise constructing a
schema-compatible dataset remains explicit caller code, which works equally
well for Hugging Face datasets, PyTorch datasets, and custom indexable data.

## Adversarial implementation checklist

The change is complete only if all of the following hold:

- default calls are bit-for-bit reproducible with the old selection path;
- pool order cannot change a seeded partition;
- duplicate, non-integral, multidimensional, and out-of-range pools fail
  before training;
- a pool exactly the requested size designates every supplied index;
- non-canary and unselected-pool records remain in training, while tails do
  not;
- public docs no longer claim that Opaque injects records;
- the guide does not claim all natural canaries are weak, does not promise a
  generic crafted canary is strong, and does not imply a low result certifies
  privacy;
- all four current training examples disclose that they use natural rows;
- docs keep the augmented dataset and its indices consistent across partition,
  training, and scoring;
- docs warn that canary-dependent sampler or horizon parameters can change the
  mechanism being compared; and
- no new comments or docstrings narrate development history or overstate what
  the API guarantees.
